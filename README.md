<h1 align="center">oMLX — Qwen3.8-27B × M5 Edition</h1>

<p align="center"><b>A specialized oMLX build for serving Qwen3.8-27B (oQ4e + native MTP) on Apple M5 Pro / Max.</b><br>
Measured: <b>230 tokens/s</b> end-to-end prefill at 262K context (cold start, M5 Pro) · decode 30+ tok/s with MTP.</p>

---

This is a specialization of [jundot/omlx](https://github.com/jundot/omlx) (Apache-2.0), rebuilt around a
single optimal serving path: **Qwen3.8-27B-oQ4e-mtp on Apple M5 Pro/Max, long-context (up to 262K) prefill.**

Everything off the optimal path was removed — other model families, ANE prefill, TurboQuant, DFlash/speculative
drafters, draft-prefix caches — and the remaining hot path was tuned on hardware (kernel sweep → shipped
defaults). Server surroundings are untouched: web UI, OpenAI-compatible API, web search, MCP, embeddings,
reranking, tool-call parsers, audio.

## What's different from upstream

| Area | Change |
|---|---|
| Model support | Converged to the Qwen3.5/3.6/3.8 family (VLM + text). Other families stripped. |
| Kernel | fa256 NAX attention: `splits=64` tuned on M5 Pro (+1.7% E2E prefill vs 32); metallib ships only the used instantiations (bq16/32/64 × bk32 × bf16/fp16) |
| Memory | Production defaults: 48 GB guard ceiling, 8 GB MLX buffer pool cap, 2048-token prefill chunks |
| Tuner | Built-in web tuner (Settings → model settings → Experimental Features): kernel sweep ~15 min, model E2E sweep at a selectable context (64K–256K). Winners apply as defaults. |
| Verified | 8,700+ tests green; growing-kL wedge sequence (128 chunks to 262K) clean; fresh-venv source install smoke-tested |

## Requirements

- Apple M5 Pro or M5 Max (the NAX attention kernel requires M5 tensor units; other Apple Silicon falls back to slower paths)
- macOS 26.2+ (SDK for the Metal toolchain)
- Python 3.11
- Xcode command line tools + CMake (native extension build)

## Install (from source)

```bash
git clone <this-repo> omlx && cd omlx
python3.11 -m venv .venv && source .venv/bin/activate
pip install -U pip
OMLX_WITH_CUSTOM_KERNEL=1 pip install -e .
python -m omlx.tuning.bench_fa256_sweep   # acceptance: >= 21 TFLOPS at 262K
```

The native extension builds during install (CMake + Metal). The NAX metallib is
generated by the build (`air-lld` order matters — see
`omlx/custom_kernels/qwen35_prefill/csrc/`).

## Quickstart

```bash
python -m omlx.cli serve --model-dir ~/.omlx/models
```

- Admin UI: `http://127.0.0.1:8000/admin` (first visit sets the API key)
- OpenAI-compatible API: `http://127.0.0.1:8000/v1/chat/completions`
- Supported model: **Qwen3.8-27B-oQ4e-mtp** (dense model; oQ4e = enhanced-calibration
  mixed 4/5-bit affine quant + native MTP head).
  Download it into the model dir, then load it from the admin Models page.
- Native MTP (draft depth up to 3) is attached automatically when `mtp_enabled` is on
  for the model.

### Tuning

Models → model settings → **Experimental Features**:

- **Kernel tuning** (~15 min): sweeps fa256 NAX split/budget parameters on your
  machine via a standalone 262K benchmark, then validates the winner against the
  growing-context wedge sequence. Ships tuned for M5 Pro; re-run on other dies.
- **Context tuning (E2E)**: end-to-end prefill benchmark of this model at a chosen
  context (64K–256K), cold cache per candidate. ~25 min at 128K.

Winners are written to `~/.omlx/tuning.json` and applied at next server start
(the panel shows which keys need a restart).

## Performance (M5 Pro, Qwen3.8-27B-oQ4e-mtp)

Measured back-to-back on the same idle machine with oMLX's built-in
benchmarks (throughput benchmark for the pp/tg rows, context benchmark for the
max-context rows), cold caches, `cached_tokens = 0` verified per run, medians
of 3 interleaved runs. Upstream v0.6.4 ran from a clean checkout with stock
defaults in an isolated environment — its context window raised to the model's
262,144 limit and native MTP enabled for parity. `pp` = prompt tokens, `tg` =
generated tokens.

| Workload | upstream v0.6.4 | **this fork** |
|---|---|---|
| Longest prefill that completes | **100,352 tok** (memory guard cap) | **262,144 tok** (full window) |
| Prefill @262,144 (prefill-only) | — | **230 tok/s** (1142 s) |
| Prefill @100,352 (prefill-only) | 274 tok/s | — |
| Prefill @4,096 + tg128 | 458 tok/s · 32.4 tok/s gen | 448 tok/s · 31.5 tok/s gen |
| Prefill @16,384 + tg128 | 427 tok/s · 34.3 tok/s gen | 426 tok/s · 33.5 tok/s gen |
| Prefill @65,536 + tg128 | 326 tok/s · 24.0 tok/s gen | **366 tok/s · 29.9 tok/s gen** |
| Prefill @131,072 + tg128 | rejected (needs ~48.5 GB) | **297 tok/s · 27.5 tok/s gen** |
| Decode @~100K ctx, 128 gen | 20.9 tok/s | **30.0 tok/s** |
| Peak Metal memory @65,536 prefill | 29.6 GB | **23.5 GB** |
| Peak Metal memory @131,072 prefill | rejected | **28.0 GB** |

Why the fork goes further: upstream's stock SDPA prefill allocates large
attention transients (≈8.5 GB by kv_len 90K), so the memory guard rejects
prompts beyond ~100K tokens on a 64 GB machine — the fork's NAX fa256 kernel
prefills the full 262,144-token window at lower peak memory and pulls ahead
on throughput as context grows.

> Other Qwen 3.5 / 3.6 / 3.8 family models and their various quantizations may
> benefit similarly from this build, but they are untested.
